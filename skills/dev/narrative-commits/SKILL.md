# Narrative Commits

変更を発生理由ごとに分け、レビュアーが上から順に読むだけで意図を追えるコミット列を作る。

## なぜこうするのか

レビュアーが確認すべき観点は、変更の理由によって異なる。挙動を変えない変更は「等価であること」だけを確かめればよく、挙動を変える変更は「仕様として妥当か」を考える必要がある。両者が1コミットに混ざると、レビュアーは全行を最も重い観点で読むことになる。

メソッドを移動しつつ中身を直すと、diffは削除80行と追加85行に見える。移動だけのコミットと、中身を直すコミットに分ければ、前者は読み飛ばせて、後者は数行で済む。この差を生むのがこのスキルの目的である。

## 手順

### 1. 現状を把握する

```bash
git status --porcelain
git diff            # 未ステージ
git diff --cached   # ステージ済み
git log --oneline -n 20
```

`git log` からリポジトリのコミット規約（接頭辞、言語、スコープの書き方）を読み取る。既存の規約があればそれに従い、このスキルの書式は規約と矛盾しない範囲で適用する。

依頼と無関係に見える変更（別作業の残り、`.env` などの秘密情報、意図不明のファイル）が混ざっていたら、コミットに含めずユーザーに確認する。

### 2. 完成形を保存する

分割の途中で中間状態を作るため、最初に完成形のツリーを記録する。最後に「全コミット適用後のツリーが完成形と完全に一致する」ことを確認するための基準になる。

```bash
cp "$(git rev-parse --git-path index)" /tmp/nc-index
GIT_INDEX_FILE=/tmp/nc-index git add -A
GOAL=$(GIT_INDEX_FILE=/tmp/nc-index git write-tree)
echo "$GOAL"
```

`GOAL` のハッシュは控えておく。シェルが変わっても参照できるようにするためである。

### 3. 変更を分類する

すべての変更を、ハンクより細かい「意図の単位」で下表の種別に分類する。1つのハンクに複数の種別が混ざっていることは普通にある。

| 種別 | Change-Kind | 挙動(既定) | 接頭辞の目安 |
| --- | --- | --- | --- |
| 機能追加 | `feature` | 変わる | `feat` |
| 仕様変更 | `spec-change` | 変わる | `feat` または `fix` |
| 機能削除 | `removal` | 変わる | `feat` |
| バグ修正 | `bugfix` | 変わる | `fix` |
| 性能改善 | `perf` | 変わる | `perf` |
| セキュリティ対応、エラーハンドリングの堅牢化 | `hardening` | 変わる | `fix` |
| 依存ライブラリ更新、API追従 | `deps` | 変わる | `build` |
| ログ、計測の追加 | `observability` | 変わる | `feat` |
| 文言、設定値、フィーチャーフラグ | `config` | 変わる | `chore` |
| リバート | `revert` | 変わる | `revert` |
| 分割リファクタ | `split` | 変わらない | `refactor` |
| 集約リファクタ | `merge` | 変わらない | `refactor` |
| 置き換えリファクタ | `replace` | 変わらない | `refactor` |
| 移動、リネーム | `move` | 変わらない | `refactor` |
| フォーマット、lint修正 | `format` | 変わらない | `style` |
| デッドコード削除 | `dead-code` | 変わらない | `refactor` |
| 型注釈の追加、厳格化 | `types` | 変わらない | `refactor` |
| コメント、ドキュメント | `docs` | 変わらない | `docs` |
| テストの追加、修正 | `test` | 変わらない | `test` |
| 自動生成コードの再生成 | `generated` | 変わらない | `chore` |
| ビルド、CI設定 | `build` | 変わらない | `build` または `ci` |

「挙動(既定)」列は種別ごとの典型であり、Change-Kindを決めれば自動で決まる値ではない。実際のBehaviorは、そのコミット時点でコードが既存の実行経路から到達可能かで判断する。`feature` / `observability` / `config` のように表では「変わる」とされる種別でも、追加した時点でまだどこからも呼ばれていない・配線されていないなら、現在のシステムの挙動は変わっていないので `Behavior: preserving` になる。これは「段階的に`feature`を導入する」シリーズでよく起きる: 新しい関数やAPIエンドポイントをまず追加し、呼び出し元を後続のコミットで切り替える構成では、追加コミットは`Change-Kind: feature`のまま`Behavior: preserving`、切り替えコミットで初めて`Behavior: changing`になる。

意図が読み取れない変更に、推測でラベルを付けない。ユーザーに聞く。誤ったラベル、特に挙動が変わる変更に「変わらない」と付けることは、ラベルがないより有害である。逆に、まだ到達不能な追加を種別の既定値だけで「変わる」と断定するのも誤りである。実際に呼ばれるようになるコミットで初めて「変わる」と書く。

### 4. コミット計画を立てる

分類した変更を、次の原則でコミットにまとめ、順序を決める。

**まとめ方**

- 1コミットは1種別、1意図とする。件名を「〜と〜」なしの一文で書けなければ、分割が足りない
- 挙動が変わらない変更と変わる変更は、決して同じコミットに入れない
- 移動と中身の変更は分ける。先に「移動だけ」のコミットを作り、次に中身を直す。移動だけのコミットは機械的に等価性を確認できるため、レビュアーは読み飛ばせる
- 整形と自動生成は、それぞれ単独のコミットにする。本文に実行したコマンドを書く
- 同じパターンの機械的な置き換えは、件数が多くても1コミットにまとめる。ただしパターンから外れる変更は別コミットに出す
- 挙動を変えるコードと、その挙動を検証するテストは同じコミットに入れる
- 細かくしすぎない。単独では意味をなさない断片に割ると、かえって流れが追えなくなる

**順序**

作業した時系列ではなく、論理的な依存関係で並べる。読み手が「変更しやすくする準備をしてから、変更する」流れとして読めるようにする。

1. 機械的な下準備: 整形、自動生成、依存更新
2. 構造の下準備: 移動、リネーム、分割、集約、置き換え、型の整備
3. 本題: 機能追加、仕様変更、バグ修正などの挙動変更
4. 後片付け: デッドコード削除、不要になったフラグの除去
5. ドキュメント

**各コミットは単独で成立させる**

どのコミットを取り出してもビルドが通り、テストが通る状態にする。途中で壊れるコミットがあると、`git bisect` が使えなくなり、レビュアーもコミット単位で動作を確認できない。依存更新でAPIが変わる場合は、更新と最小限の追従を同じコミットに入れる。

計画は表にしてユーザーに示す。

```
# 種別        挙動       件名
1 format      変わらない  style: prettierを適用
2 move        変わらない  refactor(user): validateをValidatorへ移動
3 replace     変わらない  refactor(user): 正規表現の検証をzodスキーマに置き換え
4 bugfix      変わる      fix(user): 全角スペースのみの名前を拒否する
5 dead-code   変わらない  refactor(user): 未使用のlegacyValidateを削除
```

分類や分割に迷う点がなければ、計画を示したうえでそのまま進める。迷う点があれば、そこだけ確認する。

### 5. コミットを作る

計画の順に、1つずつ次を繰り返す。

**ファイル単位で分けられる場合**

```bash
git add <files>
```

**ハンク単位で分けられる場合**

対話的な `git add -p` は使わず、パッチを編集して適用する。

```bash
git diff -- <file> > /tmp/nc.patch
# /tmp/nc.patch から、このコミットに入れるハンクだけを残す
git apply --cached --recount /tmp/nc.patch
```

**同じ行に複数の種別が混ざっている場合**

ハンクでは分けられないため、中間状態を作る。

1. 対象ファイルを、このコミット時点であるべき内容に書き換える。移動だけのコミットなら、移動元の本体を一字一句変えずに移動先へ置いた状態にする
2. その状態をコミットする
3. 完成形に戻す: `git restore --source="$GOAL" --worktree -- <file>`

中間状態は「もし最初からこの順で作業していたら存在したはずの状態」である。完成形にない新しいコードを発明しない。

**検証**

コミットの前に、その時点のツリーで実行できる確認を行う。型チェック、lint、関連テストの順に、コストに見合う範囲で実行する。挙動が変わらないコミットでは、テストを一切変更せずに通ることが等価性の証拠になる。

未コミットの変更が検証の邪魔になる場合は、`git stash push --keep-index --include-untracked` で退避してから検証し、`git stash pop` で戻す。

### 6. メッセージを書く

```
<接頭辞>(<スコープ>): <何をしたか>

なぜ: <この変更が必要になった理由。前後のコミットとの関係>
挙動: <変わらない / 変わる（何がどう変わるか）>
確認: <等価性または動作をどう確認したか>

Change-Kind: <種別>
Behavior: <preserving | changing>
```

- 件名は「何をしたか」、本文は「なぜ」を書く。コードを読めば分かることは繰り返さない
- 「なぜ」には、列の中での役割を書く。下準備のコミットなら「次のコミットで〜するため」と書くと、読み手が流れを追える
- `Change-Kind` と `Behavior` のトレーラーは、レビュー支援ツールが機械的に読むためのものである。値は3章の表のとおりに書く
- リポジトリの規約がトレーラーや本文の書式と衝突する場合は、規約を優先し、種別と挙動の有無は本文の文章で伝える
- メッセージの言語は、既存の履歴に合わせる

**例**

```
refactor(user): validateをUserServiceからValidatorへ移動

なぜ: 次のコミットで検証ロジックをスキーマに置き換えるため、
      先に検証の責務を1箇所に集める。
挙動: 変わらない。本体は変更していない。変わったのはimportと、
      this.repoを引数で受け取るようにした点のみ。
確認: 既存テストを変更せずに全件通過。

Change-Kind: move
Behavior: preserving
```

```
fix(user): 全角スペースのみの名前を拒否する

なぜ: trim()が全角スペースを除去しないため、空の名前が登録できていた。
挙動: 変わる。全角スペースのみの入力がバリデーションエラーになる。
確認: 再現テストを追加。修正前は失敗、修正後は通過。

Change-Kind: bugfix
Behavior: changing
```

### 7. 最終確認をする

全コミットの後、ツリーが完成形と一致することを確認する。

```bash
git diff --exit-code "$GOAL" HEAD && git status --porcelain
```

差分が出た場合は、分割の過程で変更を落としたか、余計な変更を加えている。原因を特定して直す。差分が残ったまま完了としない。

最後に、作成したコミットの一覧（`git log --oneline <開始点>..HEAD`）をユーザーに示す。

## やってはいけないこと

- **pushしない**。頼まれた場合のみ行う
- **既存のコミットを書き換えない**。すでにあるコミットの整理（rebaseによる分割や並べ替え）は、ユーザーが明示的に求めたときだけ行う。push済みの履歴であれば、その影響を伝えてから行う
- **完成形を変えない**。分割の途中で改善点に気づいても、勝手に直さない。気づいた点はユーザーに報告する
- **挙動の有無を偽らない**。等価性に確信が持てない変更は `Behavior: changing` とし、何が変わりうるかを本文に書く

## すでにコミット済みの履歴を整える場合

ユーザーが既存のコミット列の整理を求めた場合は、対象範囲の先頭の親まで `git reset --soft` で戻して作業ツリーの変更として扱い、上記の手順を適用する。開始前に元のHEADを控え（`git rev-parse HEAD`）、いつでも `git reset --hard <元のHEAD>` で戻せるようにする。
